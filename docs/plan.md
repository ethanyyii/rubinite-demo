# 戰鬥 Demo 開發計畫 v0.2（定案）

> v0.2 變更：改為無人值守執行。每個里程碑由 AI 自我審核，以客觀指標、模擬玩家與獨立審查取代人類試玩；最後交付自我驗證過的完整 demo 與驗收報告。

## 1. 目標

做出一場可以從頭打到尾的 Boss 戰：主角以劍彈返對抗 Boss Veltharis，兩個階段，勝利或死亡後可在 3 秒內重試。戰鬥節奏以《隻狼》的彈返為目標。

本次執行的範圍是**第一階段（機制）**，美術使用佔位圖形。正式美術是第二階段，不在本次範圍內。

## 2. 兩個階段

| 階段 | 內容 | 美術 |
|---|---|---|
| 第一階段：機制（本次） | 里程碑 M0–M6，做出所有戰鬥規則並完成自我審核 | 佔位圖形（見 §4），不花任何生成額度 |
| 第二階段：美術（之後） | 訂一個月 PixelLab Tier 1，產出素材並替換佔位圖形 | 依 `player-knight.md`、`boss-veltharis.md` §8、`arena.md` |

## 3. 無人值守的執行規則

- 依序完成 M0 → M6。一個里程碑通過 §6 的自審流程，才進入下一個。
- **不要停下來等使用者。** 使用者整晚不在。只有在 M6 完成、產出最終報告之後才結束。
- 遇到需要使用者才能解決的事（權限被拒、godot-ai 連不上、★ 規則在實作上做不到）：記在 `docs/progress.md` 的「需要使用者」，採取最保守的替代做法，繼續往下做，最後寫進報告。
- 文件裡所有「規劃時代為決定」的項目一律視為已採用，不需要再確認。
- 不下載任何東西。佔位音效用程式合成（例如簡單的波形合成），不使用外部音效包。
- 不使用 PixelLab。
- 每個里程碑通過自審後，在本機 commit（訊息以 `M0:`、`M1:`… 開頭）。不 push，不 commit `.mcp.json`。
- 隨時保持 `docs/progress.md` 最新：做到哪、怎麼驗證的、結果、偏離文件的地方。對話被壓縮或中斷後，就從這份檔案接續。
- 開工時先在背景執行 `caffeinate -dims`，防止電腦睡眠；全部完成後結束它。
- **啟動檢查（開工的第一件事）**：確認工具清單裡有 godot-ai，並實際呼叫一次 `editor_state` 確認連得上；同時確認無介面測試能跑。檢查完在**第一則訊息**用一行回報結果（例如「godot-ai 連線正常，開始 M0」）。
  - godot-ai 連不上時：檢查 Godot 編輯器有沒有開著、8000 與 9500 埠有沒有在監聽，嘗試診斷一次。
  - 仍然連不上：**不要停下來**，在 `progress.md` 的「需要使用者」記下原因，改以無介面測試加逐幀狀態紀錄繼續驗證，並在最終報告標明哪些里程碑缺少畫面驗證。

## 4. 佔位圖形規格

- 主角：藍色膠囊（腳底圓半徑 8px，高約 40px），一條白色短線指向面向（劍），腳底橢圓陰影。
- Boss：紅色大膠囊（腳底圓半徑 26px，高約 120px），灰色長方形代表大劍。（2026-09-30 起：半徑 35、高 160，見 `boss-veltharis.md` §2）
- 預兆：一般攻擊起手時劍變亮紅；延遲攻擊時劍閃爍；危險預兆為全身閃白、頭頂出現白色星形圖示，並播放提示音。
- 判定：出招時用半透明色塊預覽攻擊範圍（可用除錯開關關閉）。
- 場地：720×400px 的橢圓戰鬥區，邊緣放幾根會參與 Y 排序的柱子。（2026-09-30 起：1080×600、畫面 960×540，見 `arena.md` §2）
- 佔位圖形也要做到整齊、易讀，這是明天使用者第一眼看到的東西。

## 5. 除錯工具（M0 就要做）

| 按鍵 | 功能 |
|---|---|
| F1 | 顯示判定範圍、狀態名稱、架勢與韌性的數值 |
| F2 | 慢動作 0.25 倍（檢查幀數與預兆） |
| F3 | Boss 停止 AI，改用數字鍵 1–9 指定下一招（練習彈返） |
| F4 | 玩家無敵 |
| F5 | 重置戰鬥 |

除錯工具只在除錯建置中啟用。

## 6. 自審流程（每個里程碑都要跑完）

1. **自動測試**：`tests/unit` 全部通過；專案以零錯誤、零警告啟動。
2. **畫面驗證**：用 godot-ai 執行遊戲，依該里程碑的情境注入輸入，在關鍵時刻截圖並親自檢查畫面。截圖存到 `docs/evidence/M<n>/`。
3. **模擬玩家**（M2 起）：用腳本控制的玩家跑情境；M4 起加入整場對戰的批次模擬（見 §7）。
4. **獨立審查**：啟動一個沒有參與實作的子代理當審查員，給它該里程碑的章節、相關設計文件、程式碼與驗證證據，請它逐條檢查是否達標，並指出錯誤、偏離文件之處、程式品質問題。修正所有阻擋性問題後再審一次，最多三輪；仍未解決的寫進 `progress.md` 的已知問題。
5. **紀錄與 commit**：更新 `progress.md`，然後 commit。

## 7. 手感的客觀替代指標

手感原本要靠人類試玩判斷。無人值守時，改用下列可量測的指標逼近。數值不在目標範圍內時，可以在文件數值的 ±30% 內調整，每次調整都記在 `docs/tuning-log.md`；★ 規則在任何情況下都不能違反。

| 指標 | 目標 | 方法 |
|---|---|---|
| 數值一致 | 所有時間、距離、傷害、頓幀、震動都與文件（或 tuning-log）一致 | 測試掃描資料 |
| 輸入延遲 | 從按下到動作開始 ≤ 1 個物理幀（不含文件規定的起手） | 測試 |
| 沒有無解招式 | 「完美機器人」（每一擊都在正確時機彈返或閃身）能零傷害擊敗 Boss | 模擬 |
| 可彈返性 | 「擬人機器人」對每一招的完美彈返率 ≥ 40% | 模擬 |
| 難度 | 擬人機器人勝率 20–60%；勝場的戰鬥時間 3–5 分鐘 | 批次模擬 50 場 |
| 破韌節奏 | 只靠彈返約 2–3 套 Boss 連段破韌；只靠攻擊約 8–10 次四段連擊 | 模擬 |
| 重試速度 | 從死亡到可以操作 ≤ 3 秒 | 測試 |
| 效能 | 有畫面執行 3 分鐘，平均 ≥ 59fps，最低 ≥ 55fps | 效能監控 |
| 預兆可讀 | 每招的預兆在截圖上彼此可以區分，危險預兆清楚可見 | 截圖＋審查員 |

- 擬人機器人的初始設定：看到預兆後 0.25 秒才能反應；按鍵時機的誤差為常態分布，標準差 60ms；以完美窗口的中間為瞄準點；有 30% 的機率被延遲攻擊騙到。參數與結果都寫進報告。
- 批次模擬用 `godot --headless --fixed-fps 60` 執行，不受實際時間限制，可以比即時快很多。

## 8. 里程碑

### M0：基礎架構

- 內容：資料夾結構、輸入對應（`combat-design` §3）、佔位圖形、除錯工具、戰鬥資料的 Resource 格式、場地與鏡頭跟隨。開工第一步先 commit 目前的狀態作為基準。
- 驗收：零錯誤啟動；輸入對應與文件一致；戰鬥資料能被測試讀取；截圖可看到場地、主角、Boss 與除錯資訊。

### M1：移動與鏡頭

- 內容：`combat-design` §5 的速度與加減速、奔跑、面向、Y 排序、場地邊界碰撞。
- 驗收：各狀態的速度與加減速時間正確；注入移動輸入後位置變化符合速度；走到柱子後方時被正確遮擋；不會穿出場地。

### M2：攻擊、閃身、鎖定

- 內容：§7 閃身、§8 輕攻擊四段、蓄力重擊、取消規則、輸入緩衝、§9 鎖定。Boss 先當成不會動的木樁（有 HP 與韌性）。
- 驗收：每段攻擊的起手、判定、收招幀數；取消窗口；閃身無敵窗口與間隔；鎖定的取得與解除距離；注入四段連擊與蓄力突刺後，扣血與扣韌性正確。

### M3：格擋、彈返、受擊

- 內容：§6 格擋與彈返、架勢與回復、§10 受擊反應（踉蹌、倒地、擊飛、架勢崩潰、倒地無敵）。新增一個會定時出一招可設定攻擊的「訓練木樁」。
- 驗收：完美窗口的邊界正確；重新開窗的 0.3 秒；180° 防禦範圍；架勢計算；倒地全程無敵；逐幀注入格擋，在窗口內、外各截圖一次，兩者的回饋明顯不同。
- 這是手感的核心。審查員要特別檢查回饋（火花、頓幀、震動、音效）是否完全依照 §6 與 §12。

### M4：Boss 框架與第一階段

- 內容：`boss-veltharis` §4 的六招、§6 AI、`combat-design` §11 的霸體、短僵直、韌性、失衡與處決、懲罰技、預兆；建立 §7 的模擬機器人與批次模擬工具。
- 驗收：用測試掃描所有招式資料，檢查 `combat-design` §11.6 的九條 ★ 規則；AI 規則（架勢崩潰必用懲罰技、連續格擋三次後用灰燼衝擊、同一招不連用超過兩次、治療時的懲罰）；完美機器人零傷害擊敗第一階段；每招的預兆截圖可區分。

### M5：第二階段與完整流程

- 內容：階段轉場、第二階段強化與新招、§13 UI、§14 死亡與重試、勝利時吸收餘燼的演出（佔位）。
- 驗收：HP 50% 觸發轉場；第二階段只縮短收招與喘息，不縮短起手；死亡到重新操作 ≤ 3 秒；截圖確認 UI；完美機器人零傷害打完整場。

### M6：打擊感與調校

- 內容：§12 的頓幀、震動、閃光；程式合成的佔位音效；依 §7 的全部指標批次模擬並調校。
- 驗收：§7 的所有指標達標，或在報告中說明未達標的原因與做過的嘗試；頓幀不影響 UI 與輸入緩衝。

## 9. 最終交付

全部完成後產出 `docs/final-report.md`，內容：

1. 怎麼開始玩（在 Godot 編輯器按執行即可）與操作說明。
2. 各里程碑完成狀態與驗證方式。
3. §7 指標表：目標值、實測值、是否達標。
4. 與文件不同的數值，以及調整原因（摘要 tuning-log）。
5. 已知問題，以及「需要使用者」的事項。
6. AI 無法判斷、需要使用者親自確認的部分。
7. 給使用者的十分鐘試玩清單：依序該試哪些東西、看哪些地方。
8. 關鍵截圖。

## 10. 第二階段（美術）概要

**主路線（已採用）：骨架動畫。** 用設計圖還原的原生像素當零件，由 AI 寫程式擺姿勢輸出精靈圖，工具在 `tools/sprite_rig/`，審查標準在 `docs/animation-review.md`。不花生成額度。

1. 主角尺寸已定案：身體 40px（羽飾另計），走路動畫已完成，作為之後所有動畫的尺寸基準。
2. 每個新動作開工前，先交一份「動作簡報」讓使用者確認（關鍵姿勢、幀數、量化目標、對應設計圖的哪張動作小圖），確認後才畫。
3. 骨架做不到的姿勢（大角度旋轉、雙手握劍等）：先用原圖色盤畫新零件，並與設計圖比對通過後才加入零件庫。**格擋是最高風險的動作，建議最先做**，它做得出來，其他動作就有把握。
4. Boss 用同樣的方式，從 `veltharis-concept.webp` 還原原生像素，尺寸以 120px 為準，動畫清單見 `boss-veltharis.md` §8。（2026-09-30：實際做法與尺寸改了——不還原原生像素、身高 160，見 `art-progress.md`「Boss 動畫」）
5. 場地：產出一版不含角色、依 `arena.md` 分層的背景。
6. 接進遊戲、替換佔位圖形後，重新確認每個動作的畫格與判定時間對齊。

**備案：PixelLab。** 只在骨架動畫確實做不出的動作（例如大幅度揮劍的殘影）才評估使用，使用前先報價並取得使用者同意。

## 11. 風險

| 風險 | 對策 |
|---|---|
| AI 寫出 Godot 3 語法 | `CLAUDE.md` 列出常見錯誤；每次都要實際執行與測試 |
| 自己檢查自己，容易放水 | 由沒參與實作的子代理獨立審查；以可量測的指標為準 |
| 模擬指標不等於真實手感 | 報告中明列 AI 無法判斷的部分，由使用者用十分鐘清單確認 |
| godot-ai 整晚連線中斷 | 改用無介面測試與遊戲內截圖繼續驗證，記錄在 progress.md |
| 用量上限或對話中斷，一晚做不完 | 每個里程碑都 commit 並更新 progress.md，隨時可以從中斷處接續 |
